## TCP的三次握手和四次挥手 

服务端和客户端只是指谁先发起请求

tcp状态

* LISTEN：监听，等待连接状态
* SYN_SENT：第一次握手客户端状态
* SYN_RECV：第二次握手服务端状态
* ESTABLISHED：已建立连接
* FIN_WAIT_1：第一次挥手客户端状态
* FIN_WAIT_2：第二次挥手客户端收到ACK之后的状态
* CLOSE_WAIT：第二次挥手服务端状态
* LAST_ACK：第三次挥手服务端状态
* TIME_WAIT：第三次挥手客户端收到FIN之后的状态

### 三次握手

**因为tcp是全双工，所以要确认双方的发送和接收能力是否正常**


1. 第一次握手
   客户端向服务端发起连接请求，标志位SYN=1，序列号seq为一个随机数m
   客户端发送完 SYN 后进入 SYN_SENT 状态
   ```
   client -->            SYN=1，seq=m          --> server
   ```
2. 第二次握手
   服务端收到消息回复客户端，标志位SYN=1,ACK=1,确认号ack为m+1
   这里服务端不仅回复ACK=1，还发起连接请求，所以还有SYN=1，seq=一个随机数n
   服务端发送完红进入 SYN_RECV 状态
   客户端接收完后进入 ESTABLISHED 状态
   ```
   client <--  SYN=1，ACK=1，ack=m+1，seq=n    <-- server
   ```
3. 第三次握手
   客户端收到服务端的确认请求和连接请求，回应客户端的请求，发送ACK=1标志位，和确认号ack
   服务端收到请求后进入 ESTABLISHED 状态
   ```
   client -->          ACK=1，ack=n+1          ---> server
   ```

### 四次挥手

**因为tcp是全双工，所以每个方向都需要单独关闭**


1. 第一次挥手
   client发送完数据，准备断开连接，发送 FIN=1，序列号seq为一个随机数m
   client发送完 FIN 后进入 FIN_WAIT_1 状态
   ```
   client -->  FIN=1，seq=m    --> server
   ```
2. 第二次挥手
   服务端收到客户端的FIN请求，发送ACK=1，确认号seq=m+1
   server端 进入 CLOSE_WAIT 状态
   client收到消息后进入 FIN_WAIT_2 状态
   ```
   client <--  ACK=1，ack=m+1  <-- server
   ```
3. 第三次挥手
   服务端继续发送数据，等发送完数据后，发送FIN=1和seq=n
   server 发送 FIN 后进入 LAST_ACK 状态
   client 收到 FIN 后进入 TIME_WAIT 状态
   ```
   client <--  FIN=1，seq=n    <-- server
   ```
4. 第四次挥手
   客户端收到服务端的FIN请求，回复服务端ACK=1和确认号ack=n+1
   server 收到后 , 进入 CLOSED 状态
   client 等待 2MSL 后 , 进入CLOSED状态

   ```conf
   client -->  ACK=1，ack=n+1  --> server
   ```

**MSL**
MSL是Maximum Segment Lifetime的缩写，译为报文最大生存时间
如果 server 没有收到第四次挥手client发送的ACK，则server端会重试第三次挥手的FIN，所以需要等待 2MSL 
2MSL 的是将刚好是第二次挥手client发送给server端 + 第三次挥手server发送给client的时间总和

**tcp三次挥手**

四次挥手：
1. 服务端应用程序还有数据要发送，所以将发送 FIN 报文的控制权交给服务端应用程序
2. 

三次挥手：
1. 如果服务端没有数据要发送，并且开启了 TCP 延迟确认机制，那么第二和第三次挥手就会合并传输，这样就出现了三次挥手。 
2. TCP 延迟确认机制默认开启，所以实际 三次握手可能比四次握手还多
