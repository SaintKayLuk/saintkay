## 两种存储方式

* RDB
* AOF   
redis长期计划最终将AOF和RDB统一为一个持久性模型

四种持久化方案

* RDB(redis数据库)  按指定时间间隔执行数据库的时间点的快照
* AOF(附加文本)     记录每个写操作，在redis重启时，重建数据
* 无持久性          数据只存在于内存中，重启redis则不会存在任何数据
* RDB+AOF           4.x之前的版本，RDB和AOF不能同时存在


### RDB

快照方式存到磁盘，默认文件名 dump.rdb

几种rdb存储触发方式
* save      同步持久化到磁盘
* bgsave    异步持久化到磁盘
* 自动化    根据redis.conf中 save m n 配置(m秒内n个key改变)自动持久化到磁盘
* 退出redis 退出redis服务端的时候，会自动持久化到磁盘

相关配置文件
```conf
dir ./
save 900 1      
save 300 10     
save 60 10000   
stop-writes-on-bgsave-error yes
rdbcompression yes
rdbchecksum yes
dbfilename dump.rdb
```

### AOF

日志文件方式存到磁盘，默认文件名 appendonly.aof


相关配置文件
```conf
dir ./
appendonly no
appendfilename "appendonly.aof"
# appendfsync always
appendfsync everysec
# appendfsync no
no-appendfsync-on-rewrite no
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-load-truncated yes
aof-use-rdb-preamble yes
``` 


### 优缺点

RDB
* 优点
  * 数据文件小，非常适合做备份
  * 对于灾难恢复非常有用
  * 最大限度提高redis性能，父进程fork一个子进程来执行I/O操作
  * 与aof对比，在数据量大的时候，能够快速启动
  * 在副本上，支持重新启动和故障转移后的部分重新同步
* 缺点
  * 安全性不高，当redis出现故障未正常关闭时，可能会失去分钟级数据
  * rdb经常fork子进程来进行持久化操作，当数据量大的时候，fork可能会耗时，造成堵塞

AOF
* 优点
  * 持久化更好，不同的fsync策略，可以将损失降低到秒级
  * aof日志是仅追加日志，当停电这种情况下，则不会出现寻道，也不会出现损坏问题，即使由于某种原因(磁盘已满或其他原因)以半命令写入，也能redis-check-aof修复
  * aof文件太大时，redis可以在后台重写aof文件
  * 易于理解和解析格式的包含所有操作的日志，即使使用了flushall命令刷新了所有内容，在没有重写aof文件时，也可以停止redis，删除最新命令并启动来还原数据
* 缺点
  * AOF文件通常大于等效的RDB文件
  * 根据fsync策略，aof持久化比rdb慢




### 运作方式

RDB
1. redis主进程fork一个子进程
2. 子进程开始将数据写入临时RDB文件
3. 当子进程完成数据的写入后，临时RDB文件将会替换旧RDB文件

AOF重写过程(旧aof文件 --> 新aof文件)
1. redis主进程fork一个子进程
2. 子进程开始在临时文件中写入新aof(根据aof-use-rdb-preamble选项，会判断是否从rdb中提取数据，还是全都从内存中获取)
3. 父进程将新的更改写入内存缓冲中，同时将新的更改写入旧的aof文件中(就算重写失败，我们也能保证数据安全)
4. 当子进程完成对新aof的重写时，父进程会收到一个信号，并在新aof文件中最佳内存缓冲区数据
5. redis将旧文件改名，并将临时文件改为设定的aof文件名，并开始在新文件中追加内容
