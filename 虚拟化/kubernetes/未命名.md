# kubernetes 3 种ip

1. Node IP  ：Node节点的IP地址，即物理机（宿主机）的网卡地址
2. Pod IP   ：Pod的IP地址
3. Cluster IP：也可叫Service IP，Service的IP地址


#### Pod IP

1. 同Service下的pod可以直接根据PodIP相互通信
2. 不同Service下的pod在集群间pod通信要借助于 cluster ip
3. pod和集群外通信，要借助于node ip


#### Cluster IP

是一个虚拟ip，只能机器内部访问，Service可以为一组具有相同功能的容器应用提供一个统一的入口地址， 并且将请求负载分发到后端的各个容器应用上，可以将后端的多个容器看做一个集群，Service是集群的入口。所以Service IP也叫做Cluster IP

1. Cluster IP仅仅作用于kubernetes Service这个对象，并由Kubernetes管理和分配IP地址（来源于Cluster IP地址池）
2. Cluster IP无法被ping，因为没有一个“实体网络对象”来响应
3. Cluster IP只能结合Service Port组成一个具体的通信端口，单独的Cluster IP不具备TCP/IP通信的基础，




# kubernetes 各种服务发现

1. 集群内 --> 集群内
2. 集群内 --> 集群外
3. 集群外 --> 集群内




#### 集群内 --> 集群内

例：pod A 要访问 pod B

1. pod A 直接访问 pod B 的PodIP
2. pod A 访问 pod B 的service的ip(Cluster IP)，也可以通过DNS访问service的名字
3. pod A 访问 pod B 的HeadlessService，(HeadlessService会返回所有的podB的ip)



#### 集群内 --> 集群外

例：pod A 访问外部 Mysql

1. 直接访问Mysql的ip和port
2. 定义一个service，不定义label，定义一个Endpoint，里面配置Mysql的ip和port，也可以通过dns来访问service的名字


#### 集群外 --> 集群内

例：client 访问 集群内的 pod A

1. 通过访问 Nodeport，nodeport会在每个节点占用端口，再转发到pod A的service
2. 访问 hostport ，在单个节点上开启端口，就是简单的宿主机端口映射
3. 通过 Ingress 访问服务




# labels
yaml文件的标签，每个资源都可以有1个或者多个label

spec.selector 选择的时候，选择符合所有符合的标签

例如,标签选择器选择2个标签，则符合这2个标签的资源才会被选中，如下test1会被选中，test2不会被选中
```yaml
spec:
  selector:
    matchLabels:
      aaa: abc
      bbb: bcd
---

name: test1
metadata:                       
  labels:
    aaa: abc
    bbb: bcd
    ccc: cbc     

---

name: test2
metadata:                       
  labels:
    aaa: abc
    bbb: dcd

```
上级选择的时候，需要符合上级标签选择器的所有标签，可以多，但不能少


```sh
#给k1节点添加一个 aaa=bbb 的标签
kubectl label nodes k1 aaa=bbb

#删除k1节点的 aaa=bbb 标签，标签的键跟着 - 即为删除
kubectl label nodes k1 aaa-
```





## cgroup 驱动

cgroup v1
cgroup v2


* cgroupfs：早期kubelet默认的驱动
  * 支持cgroup v1
* systemd：
  * 支持 cgroup v1 和 cgroup v2



当 systemd 是初始化系统时，推荐使用 systemd，可以通过以下命令查看
```sh
ps -p 1
```


如果设置 systemd 为 cgroup驱动，则 kubelet 和 runtime 都需要设置

###### kubelet 设置
1.22 开始，如果没有指定，则默认是 systemd 驱动
```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
...
cgroupDriver: systemd
```

###### containerd 设置
编辑 /etc/containerd/config.toml
```toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
  ...
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
    SystemdCgroup = true
```

如果是包安装，例如rpm 或 .deb ，则还需要在 disabled_plugins 中去除 cri
```
disabled_plugins = []
```

修改完重启 containerd
```sh
systemctl restart containerd
```

#### 为什么系统使用 systemd 的时候要使用 systemd cgroup 驱动
当某个 Linux 系统发行版使用 systemd 作为其初始化系统时，初始化进程会生成并使用一个 root 控制组（cgroup），并充当 cgroup 管理器。

systemd 与 cgroup 集成紧密，并将为每个 systemd 单元分配一个 cgroup。 因此，如果你 systemd 用作初始化系统，同时使用 cgroupfs 驱动，则系统中会存在两个不同的 cgroup 管理器。

同时存在两个 cgroup 管理器将造成系统中针对可用的资源和使用中的资源出现两个视图。某些情况下， 将 kubelet 和容器运行时配置为使用 cgroupfs、但为剩余的进程使用 systemd 的那些节点将在资源压力增大时变得不稳定。

当 systemd 是选定的初始化系统时，缓解这个不稳定问题的方法是针对 kubelet 和容器运行时将 systemd 用作 cgroup 驱动。
