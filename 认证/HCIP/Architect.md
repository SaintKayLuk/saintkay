企业应用架构设计五大原则

* **安全**：通过对系统的安全性评估，在提供业务价值的同时保护信息、系统和资产的能力。
* **性能**：有效地使用资源以满足系统要求的能力，比如计算资源性能，网络资源性能，存储资源性能，数据资源性能。
* **成本**：避免或消除不必要的成本或不够理想的资源的能力。
* **可用性**：系统从基础设施故障或服务故障恢复、动态获取资源以满足需求以及减少中断的能力，在设计中考虑单AZ可用性，跨AZ容灾，跨AZ双活，异地容灾部署。
* **可扩展性**：应用系统可扩展性是指该系统适应变化的能力，可以根据用户数量或者业务流量进行扩展的能力，如水平扩展能力，垂直扩展能力。

# 3. 网络服务规划

云上网络，或云管理网络可为时下流行的分布式架构提供服务

* 云上网络
  * 云上通用网络：VPC(虚拟私有云)、安全组、网络ACL
  * 云内同区域互通：VPCEP(VPC终端节点)、VPC-Peering(VPC对等连接)
  * 云内跨区域互通：云专线、云连接CC、VPN
  * 云上云下互通：云专线、VPN
* 云上网络接入：EIP、NAT网关、ELB、云解析服务

**跨区->云连接，云上云下->云专线**



网络规划设计原则
* 隔离性
  * 默认不同区域VPC之间内网不互通
  * 默认同区域不同VPC内网不互通
* 扩展性
* 连接性

VPC网络规划
1. VPC在哪个区域创建，建议在服务所在地区
2. 需要多少个VPC
3. 网段如何划分
4. 不同区域网段不建议有重合，与企业内网网段也不建议有重合






#### 安全组和网络ACL区别

**安全组对ECS进行防护**
**网络ACL对VPC子网进行防护**

| 对比项   | 安全组                                                             | 网络ACL                                                                                                                             |
|-------|-----------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| 防护对象 | ECS级别操作                                                        | 子网级别操作                                                                                                                        |
| 配置策略 | 仅支持允许策略(部分地区支持拒绝策略)                               | 支持允许、拒绝策略                                                                                                                   |
| 优先级   | 多个规则冲突，先根据绑定安全组的顺序生效，再根据组内规则的优先级生效 | 多个规则冲突，优先级最高的规则生效，优先级低的不生效                                                                                  |
| 报文组   | 仅支持报文三元组(协议、端口和对端地址)过滤                          | 支持报文五元组(协议、源端口、目的端口、源地址和目的地址)过滤                                                                           |
| 应用操作 | 创建ECS默认必须选择安全组，默认安全组自动应用到ECS                  | <li>创建子网没有网络ACL选项，即非必要选项<li>必须创建网络ACL、添加关联子网、添加出入规则，并启用网络ACL，才可应用到关联子网及子网下的ECS |




#### 安全组和云网络ACL设计原则
|        | 安全组设计原则                                                                                                                                     | 网络ACL设计原则                                                                                                      |
|--------|------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| 入方向 | <li>按资源进行划分安全组<li>最小权限原则，即每条规则都是业务必须，且每条规则都有明确的ip范围和端口<li>对端IP可以是网段或者具体IP地址<li>端口需要限制 | <li>建议VPC内子网默认互通，不限制<li>尽量减少VPC之间互通，只有固定网段可以互通<li>只控制边界子网，例如ELB子网和数据子网 |
| 出方向 | 默认全通                                                                                                                                           | 默认全通                                                                                                             |





#### 对等连接 VPC-peering

1. 使两个VPC之间的子网互通，就像两个VPC在同一个网络
2. 不建议两端VPC的网段（CIDR）存在重叠
3. 如果两个VPC的CIDR有重叠，建立对等连接时，只能针对子网建立对等关系
4. 两个VPC之间不能同时建立多个VPC对等连接
5. VPC对等连接不支持传递的对等关系，例如A和B，A和C 都建立了VPC对等连接，但是B和C不能通信，必须B和C也建立VPC对等连接
6. 不同区域的VPC不能创建对等连接
7. 创建对等连接，需要向建立对等连接的VPC发送请求
8. 同账号内同区域的VPC创建对等连接，默认接受
9. 其他账号内同区域的VPC发送VPC对等连接请求，需要其他账号接受


#### VPC终端节点 VPCEP


#### PC对等连接和VPC终端节点区别
| 对比项     | VPC对等连接                           | VPC终端节点                                                                                      |
|----------|-------------------------------------|------------------------------------------------------------------------------------------------|
| 安全性     | VPC内所有ECS,ELB均可被访问            | 仅创建了Endpoint Service的ECS、ELB等可以被访问                                                    |
| CIDR重叠   | 不支持                                | 支持                                                                                             |
| 通信方向   | 建立对等连接的两个VPC之间支持双向通信 | 通过VPC终端节点建立连接的两个VPC之间，仅支持终端节点所在VPC访问终端节点服务所在后端资源的指定端口 |
| 路由配置   | 需要在两端VPC内分别添加路由           | 无需自己配置                                                                                     |
| VPN/DC访问 | 支持                                  | 支持                                                                                             |


1. 对等连接相当于两个VPC子网在同一网络
2. VPC终端节点是将VPC中的实例暴露出来，通过网关将实例端口映射到其他VPC中
3. 对等连接一般用于同一租户规划自己的网络
4. VPC终端节点主要是将服务在云平台中提供给另一租户使用

# 4. 存储服务规划

根据服务器类型分为
* 封闭系统的存储
* 开放系统的存储
  * 内置存储
  * 外挂存储
    * 直连式存储 DAS
    * 网络化存储 FAS
      * **网络接入存储 NAS**
      * 存储区域存储 SAN

DAS：比较古老了，适用于数据量不大，对磁盘访问速度要求较高的中小企业
NAS：多用于文件服务器，用来存储非结构化数据，受限于以太网速度，但是部署灵活，成本低
SAN：适用于大型应用或数据库系统，成本高，较复杂
块存储：将数据拆分成块，并单独存储各个块
文件存储：数据以单条信息的形式存储在文件夹中
对象存储：一种扁平结构，文件被拆分成多个部分并散布多个硬件间

#### 华为云存储

#### 对象存储服务OBS

可供用户存储任意类型和大小的数据。
适合企业备份/归档、视频点播、视频监控等多种数据存储场景。

Bucket(桶) --> Object(对象)

* Object
  * key：对象的名称
  * metadata：元数据，对象的描述信息
  * data：数据，即文件的数据内容
* OBS四种存储类别
  * 标准存储
  * 低频访问存储
  * 归档存储
  * 深度归档存储(受限公测中)

1. 生命周期管理功能：定时删除bucket中数据，或者转换存储类别
2. 跨区域复制：将一个bucket中的数据 自动、异步 复制到其他区域的 bucket 中
3. 多版本控制功能
4. 服务端加密功能：数据在远端加密存储，当用户读取数据时，先解密再提供给用户
5. 事件通知功能


#### 弹性文件服务SFS

2. 只能给ECS，BMS，容器使用，不能直接访问
3. 专属弹性文件服务（SFS Turbo）：独享专属计算和资源，与其他租户资源物理隔离


#### EVS和SFS和OBS的区别

|推荐场景|需要对整个云服务器进行保护|系统盘没有个人数据，因而只需要对部分的数据盘进行备份|需要对文件系统的数据进行保护|需要在云上对云下服务器的备份数据进行管理，在云上使用云下数据恢复服务器等|需要将单个或多个文件备份上云，并且可以使用备份快速恢复数据|
|优势|备份的同一个服务器下的所有磁盘数据具有一致性<br>即同时对所有云硬盘进行备份，不存在因备份创建时间差带来的数据不一致问题|保证数据安全的同时降低备份成本|备份数据与文件系统分开存放，可以使用备份创建新的文件系统|云下数据可以用于在云上搭建新的业务，将数据在云上备份|无需再以整机或整盘的形式进行备份，降低备份成本|

#### 容灾方案

存储容灾服务 SDRS 


容灾和备份具有以下区别：
* 容灾主要针对火灾、地震等重大自然灾害，因此生产站点和容灾站点之间必须保证一定的安全距离；备份主要针对人为误操作、病毒感染、逻辑错误等因素，用于业务系统的数据恢复，数据备份一般是在同一数据中心进行。
* 容灾系统不仅保护数据，更重要的目的在于保证业务的连续性；而数据备份系统只保护不同时间点版本数据的可恢复。一般首次备份为全量备份，所需的备份时间会比较长，而后续增量备份则在较短时间内就可完成。
* 容灾的最高等级可实现RPO=0；备份可设置一天最多24个不同时间点的自动备份策略，后续可将数据恢复至不同的备份点。
* 故障情况下（例如地震、火灾），容灾系统的切换时间可降低至几分钟；而备份系统的恢复时间可能几小时到几十小时。

# 8. 云原生应用架构

架构演进，演进不代表单体架构和SOA架构不适用，只是针对的产品或者企业不同，选择权变多了
```
单体架构 --> SOA架构 --> 微服务架构
```

* 单体架构
  * 复杂性高
  * 服务性能问题
  * 扩缩容能力受限
  * 无法做故障隔离
  * 发布的影响范围较大
  * 部署速度逐渐变慢
* SOA架构 **(面向服务架构)**
  * ESB服务总线
* 微服务架构
  * 松耦合去中心化
  * 独立迭代
  * 独立部署和扩展
  * 孤立容错
  * 分布式开发

##### 云原生架构演变(微服务的架构演变)
```
1. 服务治理能力内嵌在业务代码中，例如SOA、ESB
      ↓
2. 服务治理能力抽象到统一SDK实现，例如Spring Cloud
      ↓
3. 服务治理能力归一到服务网络
```

网络拓扑策略的更新和单机数据的汇报。在这种模型中，每个服务都将有一个伴随代
理SideCar，服务之间仅通过SideCar代理进行通信。这就是以Istio为代表的第二代
Service Mesh（由Google、IBM、Lyft等公司推出Istio）。
